# Phase 19 — Next enrollment session

- **Status:** Design approved section by section, 2026-10-05; implemented on branch
  phase-19-next-enrollment-session. Deviations from the approved design are folded in.
- **Date:** 2026-10-05
- **Source:** the one-pager `drafts/2026-10-04-next-enrollment-session-one-pager.md`, the design
  dialogue recorded here, and a side research on job infrastructure
  (`drafts/2026-10-04-async-jobs-infra-decision.md`, with its prompt beside it). `drafts/` is
  gitignored, so the verdict this spec depends on is restated in §1.
- **Touches:** ADR 0001 (a second entry point beside `app.ts`), ADR 0003 (the session wire
  contract), and a new ADR 0007. It also fixes the semantics of `POST /sessions`.

## Goal

A learner who has saved words (phase 18) practises them. After the seeded first session, every
session of an enrollment is built from that enrollment's saved senses, with distractors
generated by the LLM in the background. A session in progress is kept and resumed, and any
unfinished session can be skipped.

**Done means:**

1. A learner saves some senses, taps **צור שאלות**, and once the session is ready every question
   in it comes from those senses. None come from the seed.
2. After switching enrollment, the next session draws from the other enrollment's list.
3. A learner with an empty list sees a "save some words first" state instead of an empty or
   seeded session.
4. A learner who leaves mid-session sees **המשך** on the home screen and continues at the same
   question. **דלג** ends any unfinished session, the seed included.
5. `npm test`, `npm run test:all`, `npm run lint:arch`, `npm run e2e` and `npm run eval` pass,
   the last without lowering `TIER2_THRESHOLD`.

## Scope

**In:**
- pg-boss as the job infrastructure, behind a two-function port, with ADR 0007 and its check
  script;
- a `status` and a `source` on `sessions`, with at most one open session per enrollment;
- list-built sessions: senses picked at request time, distractors generated by one LLM call in
  a `prepare-session` job, stored as enrollment-owned `questions` rows;
- create-next, read, current and skip routes, and a 409 on answering a session that is not
  `ready`;
- the home screen's start / create / preparing / resume / skip / failed states, skip inside a
  session, and "next session" on the results screen;
- eval cases for the distractor prompt.

**Out:**
- knowledge levels or progress per sense;
- spaced repetition, or any ordering by past results;
- question types beyond today's multiple choice (form drills, reverse direction);
- a push notification when a session is ready;
- scheduled jobs, and `schedule` on the port;
- a separate worker process or deploy topology;
- reusing generated questions across sessions: every list session is a fresh generation.

## 1. Job infrastructure: the verdict

**Adopt pg-boss (v12) on the app's own Postgres, with the worker running in the API process,
behind a small port.** The research compared a custom Postgres table, pg-boss, Graphile Worker,
BullMQ, RabbitMQ (Amazon MQ), SQS with EventBridge, and durable-workflow engines, at the
expected year-one scale of about 100k jobs a day. The reasons, in brief:

- **Transactional enqueue is native.** `send(…, { db: fromDrizzle(tx, sql) })` enqueues inside
  the caller's Drizzle transaction, so a row and its job commit together. Only pg-boss, Graphile
  Worker and a custom table offer this. BullMQ's Postgres backend does not, and every broker
  needs an outbox.
- **Lanes cost nothing.** pg-boss lives in a `pgboss` schema of whatever database
  `DATABASE_URL` names, so each lane and each cloned test database is isolated with no new env
  value and no new container (ADR 0006).
- **Cron fires once across instances by design**, which covers the scheduled jobs expected in
  later phases.
- **It fits ADR 0002.** `new PgBoss(…)` is an ordinary constructor, so the instance is built at
  the composition root and passed down. There is no module singleton.
- **100k jobs a day is about 1.2 jobs a second.** Documented Postgres-queue failures start at
  thousands a second, or with a long transaction pinning xmin, which ADR 0001 R8 already forbids.

The alternatives' gaps were structural. Graphile Worker leaves a crashed worker's job locked for
four hours without its paid tier. Amazon MQ costs about $85–260 a month. SQS needs an outbox and
has no local scheduler emulator. A custom table is the best technical fit but means about
1,000–1,500 lines re-solving what pg-boss has already solved.

**Main risk:** a single-maintainer library with yearly breaking majors. **Switch signals:**
- hosting lands on Lambda only, then SQS with an outbox;
- concurrency caps keep tripping the Gemini quota, then BullMQ on Postgres;
- queue load shows in Postgres bloat, then SQS for the bulk queues only.

## 2. Data model

### `sessions`

```
sessions
  + status  text not null   check in ('preparing','ready','completed','skipped','failed')
  + source  text not null   check in ('seed','list')

  UNIQUE INDEX sessions_one_open_per_enrollment (enrollment_id)
    WHERE status IN ('preparing','ready')
```

- **"In progress" is not a status.** It is `ready` with at least one answer, and that is the
  only thing the home screen needs to tell **התחל** from **המשך**.
- **`completed_at` stays** as the completion timestamp, and `completeSession` sets both it and
  `status = 'completed'` in its existing write.
- **The partial unique index is the one-open-session rule as a constraint.** A concurrent second
  create fails on it and becomes a 409. `failed` and `skipped` are not open, so neither blocks
  the next create.
- **The next-source rule:** an enrollment's next session is `seed` if the enrollment has no
  session at all, and `list` otherwise. A skipped or failed session counts, so skipping the seed
  moves the learner on to the list.

### `questions`

No schema change. The owner columns phase 16 left on `questions` are written for the first time.

- **A generated question is an enrollment-owned row:**
  - `user_id` and `enrollment_id` are the session's;
  - `sense_id` is the saved sense, and `prompt_variant_id` is the entry's saved form;
  - `options` holds the correct translation and three distractors, with the correct option at
    canonical position 0. The shown order is shuffled per session by `pickQuestions`, so storing
    it first gives nothing away;
  - `id` is a fresh uuid.
- **`session_questions` points at those rows exactly as it does at seed questions**, so
  `loadSession`, `step`, scoring and the answer path are unchanged.
- **The seed pool narrows to shared questions** (`user_id IS NULL`). `loadQuestionPool`'s
  per-learner branch was a placeholder, and keeping it would let a seed session draw generated
  rows.
- **Generated rows are never reused.** Each list session is its own generation, so rows
  accumulate per session. That is about 10 rows per session and is accepted.

### Migration

One drizzle migration adds both columns and the index.

- Sessions with `completed_at` set become `completed`.
- Sessions without it become `skipped`. Nothing ever resumed them, and marking them `ready` would
  greet every existing learner with a stale **המשך**.
- Every existing session becomes `source = 'seed'`, so each existing enrollment's next session
  is built from its list, as the rule says.

The pg-boss schema is installed by `db/jobs.ts` (`installJobs`), which `runMigrations` calls
right after drizzle's migrations, not lazily at `boss.start()`. Every place that migrates a
database therefore installs it, with no new call site. The integration buckets clone a template
database, so `pgboss` must already be in the template.

## 3. Job infrastructure in the server

### The port

Two functions. `schedule` waits for its first consumer.

- **`enqueue` is transaction-bound.** `Repos` gains a `jobs` member beside `session` and
  `question`. `repo/jobs.ts` implements it as `boss.send(name, data, { db: fromDrizzle(tx, sql) })`,
  so services enqueue inside their one `transaction(…)` call and R8 is untouched.
- **`handle` is registration, in a new `worker.ts`**, a sibling of `app.ts`. `app.ts` maps
  routes to service calls, and `worker.ts` maps queue names to service calls with each queue's
  options. It holds no logic.
- **`domain/jobs.ts` holds the job names and their payload schemas.** They live in `domain/`
  rather than `services/` because `repo/jobs.ts` and `db/jobs.ts` need the names, and ADR 0001 R4
  forbids `repo/` and `db/` from importing `services/`.
- **The service methods pg-boss calls take `unknown` and parse the payload with zod themselves.**
  That keeps `worker.ts` free of logic, and a payload enqueued by an older deploy that reaches a
  newer worker fails loudly.

### Lifecycle

`index.ts` owns it:

1. constructs `PgBoss` on the existing `DATABASE_URL`, with `migrate: false` since §2's
   migration step already installed the schema;
2. starts it, and calls `registerWorkers`;
3. on SIGTERM, closes the HTTP server, then `boss.stop()` drains in-flight handlers, then closes
   the pool.

The worker runs in the API process. A separate worker container is a deploy decision, and
nothing in this design has to change to make it.

`createServerDeps` receives the boss the way it receives `db`: constructed in `main()`, never in
`composition.ts`, which performs no I/O (ADR 0001 R6).

### `prepare-session` queue options

| Option | Value | Why |
|---|---|---|
| `retryLimit` | 2 | a model answer that fails validation is usually fine on retry |
| `retryBackoff` | true | a 429 from Gemini becomes a later retry |
| `expireInSeconds` | 240 | twice the generation budget, so a crashed worker's job expires and retries |
| `localConcurrency` | 4 | stays under the Gemini quota |
| `deadLetter` | `prepare-session-failed` | one place where every terminal failure lands |
| `deleteAfterSeconds` | 86 400 | one day of history, not the 7-day default |

**Every terminal failure goes through the dead-letter queue.** Its handler,
`sessions.failPreparation(data)`, sets `failed` only while the status is still `preparing`.
Exhausted retries and expired jobs both end there, so nothing needs a sweeper. It parses only
`session_id` from the payload, so a payload that `prepareSession` refused on every attempt
still ends the session `failed`.

### ADR 0007 — Background jobs

Written with the `create-adr` skill, with `scripts/check-adr-0007-background-jobs.sh`. Rules:

1. `pg-boss` is imported only by `index.ts`, `composition.ts`, `worker.ts`, `db/jobs.ts` and
   `repo/jobs.ts`. `new PgBoss` appears only in `index.ts` and `db/jobs.ts`, the two places that
   already open connections.
2. No `.send(` or `.insert(` on the boss outside `repo/jobs.ts`, so every enqueue goes through a
   transaction.
3. `.work(` appears only in `worker.ts`.
4. A handler registered in `worker.ts` calls one service use case and nothing else. This one is
   enforced by review, like ADR 0001 R9.

ADR 0001 gains a line that `worker.ts` is an entry point with `app.ts`'s obligations: it wires
and holds no logic.

## 4. API

All schemas live in `packages/core` (ADR 0003), and every route uses `createRoute`.

### Create next — `POST /sessions` (changed)

```
{ enrollment_id }  →  201 { session_id, status, source }
```

- **Seed:** created synchronously, as today, and returned `ready`.
- **List:** one transaction picks up to 10 saved senses uniformly with the injected rng, inserts
  the `preparing` row, and enqueues `prepare-session { session_id, picks: [{ sense_id, variant_id }] }`.
  The response is `preparing`.
- The first question is no longer in the response, because a list session has none yet. The app
  reads the session instead.

This is a breaking change to `POST /sessions`. App and server ship together, as in every phase
so far.

### Read — `GET /sessions/{id}` (new)

```
→ 200 { session_id, status, source, position: { position, total }, question: Question | null }
```

`position` and `question` have the shapes next-step uses. `question` is the current one while the
session is `ready` and incomplete, and `null` otherwise. This route serves
resume and the poll. `id` stays `z.string()`, so a malformed id is a 404, as on next-step.

### Current — `GET /enrollments/{id}/sessions/current` (new)

```
→ 200 { current: { session_id, status, source, answered, total } | null,
        next_source: 'seed' | 'list',
        saved_count: number }
```

- `current` is the enrollment's newest session if its status is `preparing`, `ready` or `failed`,
  and `null` otherwise. A failed session stays visible until the next create, so a failure is
  never silent.
- `total` is the number of questions the session holds, so 0 while `preparing`.

### Skip — `POST /sessions/{id}/skip` (new)

```
→ 200 { session_id, status: 'skipped' }
```

- Allowed from `preparing` and `ready`, and idempotent on `skipped`.
- **Skip while preparing:** the job's final write is conditional on `preparing` (§5), so a job
  that finishes after a skip writes no questions.

### Next step — `POST /sessions/{id}/next-step` (changed)

The same, plus a 409 when the session's status is not `ready`. A completed session's replay still
answers 200, because `completed` sessions keep today's replay path.

## 5. The generation job

`prepare-session` calls `sessions.prepareSession({ session_id, picks })`. It has the read,
call, write shape that translations established under ADR 0001 R8's amendments:

1. **Read**, in one short transaction.
   - If the session is not `preparing`, return. No LLM call is made for a skipped session.
   - For each pick, load the saved form, the lemma, the part of speech, and the correct
     translation: the rendering of that variant and sense in the enrollment's source language.
2. **One LLM call for the whole session**, outside any transaction.
   - Up to 10 items. For each, ask for three wrong but plausible options in the source language:
     the same part of speech and register, and not a synonym of the correct answer.
   - The prompt is built from the language pair, as phase 16 does for translations.
   - Schema: `{ items: [{ sense_id, distractors: [string, string, string] }] }`.
   - Its own budget: `SESSION_GENERATION_TIMEOUT_MS`, default **120 000**, received by
     `createServerDeps` like `translationTimeoutMs`.
3. **Validate**, in a pure domain function.
   - Every pick is covered, and each item has exactly three non-empty distractors.
   - The distractors are distinct from each other and from the correct translation, compared
     after `normalizeForm`.
   - Any failure fails the whole attempt, and pg-boss retries it. A partial session would be a
     quiet surprise, and the model is non-deterministic enough that a retry usually lands.
4. **Write**, in one transaction.
   - `UPDATE sessions SET status = 'ready' WHERE id = $1 AND status = 'preparing'`. Zero rows
     means it was skipped meanwhile: return without writing.
   - Otherwise insert the enrollment-owned `questions` and the `session_questions`. The shown
     order comes from `pickQuestions` over the generated pool, so presentation is the same code
     seed sessions use.

The status flip and the question inserts are dependent writes (ADR 0001 R8): a `ready` session
with no questions, or questions on a skipped session, would each be wrong. So they share one
transaction.

## 6. Errors

| Case | Status | Error |
|---|---|---|
| unknown enrollment, on create or current | 404 | `EnrollmentNotFound` (existing) |
| unknown or malformed session id, on read, skip or next-step | 404 | `SessionNotFound` (existing) |
| an open session already exists | 409 | `SessionOpen` (new), from the unique index |
| next source is `list` and the list is empty | 409 | `NoSavedWords` (new) |
| next source is `seed` and the pair has too few questions | 409 | `InsufficientQuestions` (existing) |
| skip a `completed` or `failed` session | 409 | `SessionNotSkippable` (new) |
| answer a session that is not `ready` | 409 | `SessionNotReady` (new) |
| the model's answer fails validation | none on the wire | `InvalidDistractors` (new), thrown in the job so pg-boss retries |

The 409 bodies carry distinct `error` strings, so the app can tell `session_open` from
`no_saved_words` without parsing prose.

## 7. Mobile

### Home

Driven by `GET …/sessions/current`. It is fetched on focus, and polled every 3 s while
`current.status` is `preparing` and the screen is focused.

| State | Shown |
|---|---|
| no current, `next_source: seed` | **התחל**: create, then enter |
| no current, `list`, `saved_count > 0` | **צור שאלות** |
| no current, `list`, `saved_count = 0` | a "save some words first" line, linking to translate |
| `preparing` | disabled **מכין שאלות…** with a spinner, and **דלג** |
| `ready`, `answered = 0` | **התחל** and **דלג** |
| `ready`, `answered > 0` | **המשך** and **דלג** |
| `failed` | a short failure notice and **צור שאלות** |

### Session and results

- **The session header gains דלג.** It confirms with an alert, since the answers so far are
  discarded, then goes home.
- **Results' "practise again" becomes "next session".** It creates the next session and goes
  home, where a list source shows **מכין שאלות…**. It no longer enters a quiz directly, because a
  list session cannot be ready at that moment.

### State

- **A new `useNextSession` hook** owns `current`, `create`, `skip` and the polling.
- **`useSession.start()` becomes `enter(sessionId)`.** It loads `GET /sessions/{id}` and continues
  from the current question, so starting and resuming share one path.
- Both hooks are constructed at the composition root with the api client passed in (ADR 0002).

## 8. Testing

### Unit

**Server:**
- picking: at most 10, uniform under the injected rng, fewer when the list is short;
- distractor validation: shape, count, distinctness after normalisation, a distractor equal to
  the answer, an uncovered pick;
- `prepareSession` with fakes: the skip no-op on both the read and the conditional write, and a
  validation failure that throws;
- the next-source rule;
- `failPreparation` sets `failed` only from `preparing`.

**Mobile:**
- the home screen renders all seven states;
- polling starts on `preparing` and stops otherwise;
- skip confirms inside a session;
- `enter` resumes at the right position.

### Integration

Against real Postgres and pg-boss on the cloned database, with MockServer standing in for Gemini.

- **Through the queue:** create a list session, run the worker, and the session is `ready` with
  enrollment-owned questions.
- **Transactional enqueue:** a create whose transaction rolls back leaves no job, and a committed
  one leaves exactly one.
- **Failure:** MockServer answers 500 three times, and the session ends `failed` via the
  dead-letter queue. The test runs in real time, not on `TestClock`: two retries with a backoff
  starting at 1 s finish in under 10 s.
- **Skip races:** skipped while preparing, the job's finish writes nothing.
- **One open session:** a second create is 409 `session_open`.
- **Migration:** old completed and unfinished sessions map to `completed` and `skipped`, and the
  next session afterwards is `list`.
- **Seed isolation:** the seed pool never contains enrollment-owned questions.
- **Routes:** every status in §6.

### E2E

1. A learner completes the seed.
2. They save four senses on the translate screen.
3. They tap **צור שאלות**, wait for **התחל**, and every prompt is one of those four forms.
4. A skip mid-session returns home.
5. The "save some words first" state is covered after skipping the seed: a fresh enrollment's
   first session is the seed by §2's next-source rule, so an enrollment with an empty list does
   not reach it directly. Enrollment isolation is pinned by a server integration test instead:
   `currentSession` keeps one enrollment's session out of another's.

MockServer serves the distractor answer, in the e2e namespace.

### Eval

New cases in `apps/server/tests/eval/` for the distractor prompt: about eight senses across
`ru → he` and `en → he`.

- **Tier 1, zero failures:** the shape, three distinct distractors per item, none equal to the
  answer, all in the source language's script.
- **Tier 2, under the existing `TIER2_THRESHOLD`:** each case lists known synonyms of its answer,
  and none may appear as a distractor. This catches the worst failure, a "wrong" option that is
  right.

### ADR 0007 check script

Rules 1–3 each get a planted violation, which is confirmed to fire and then removed, before the
script is trusted (CLAUDE.md).
